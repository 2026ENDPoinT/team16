# 서버 구조와 수정 지점 (유지보수 가이드)

## 1. 데이터 처리 흐름

```text
Unity A / Unity B
    | HTTP + JSON
    v
127.0.0.1:8000 (Uvicorn)
    |
    v
FastAPI
    | app/api/v1/rooms.py, events.py   [주소/HTTP 요청]
    | app/schemas/                     [JSON 검증/응답 형식]
    v
app/services/                         [업무 처리 규칙]
    v
app/repositories/                     [DB 읽기/쓰기]
    v
app/db/models.py                      [테이블 정의]
    v
SQLite (data/tamagotchi.db)           [영구 저장]
```

## 2. 왜 이렇게 나누었는가?

현재 Unity 앱의 최종 데이터 구조를 알 수 없으므로, 특정 다마고치 속성(HP, 과제, 레벨 등)을 서버 코드에 강하게 연결하지 않았습니다. 대신:

- **Room(방)**: 같은 ID를 공유하는 Unity 프로그램들의 공유 상태 저장 단위
- **State(상태)**: 임의의 JSON 객체 (예: `{"hp":80, "score":100}`)
- **Event(이벤트)**: `sender_id`, `event_type`, `payload`를 가진 메시지. 각 클라이언트가 번호를 기준으로 가져감

이렇게 설계하면 Unity가 완성된 뒤 세부 필드를 정의하는 작업을 최소 범위에서 수행할 수 있습니다.

## 3. 파일별 책임

| 파일/폴더 | 역할 | 변경이 필요한 예시 |
|---|---|---|
| `app/main.py` | FastAPI 생성 및 실행 초기화 | 미들웨어, CORS, 시작 작업 추가 |
| `app/core/config.py` | 주소, 포트, DB 설정 | 다른 저장소 주소 적용 |
| `app/api/v1/*.py` | API 메서드 및 URL | `/users`, `/tasks` 등 새 기능 추가 |
| `app/schemas/*.py` | 주고받을 JSON 구조 | Unity에서 보낼 요청 필드 추가 |
| `app/services/*.py` | 업무 규칙 | 경험치 계산, 데이터 접근 정책 |
| `app/repositories/*.py` | SQLAlchemy DB 작업 | 검색, 정렬, 페이지네이션 로직 |
| `app/db/models.py` | SQLite 테이블 정의 | 사용자/다마고치 전용 테이블 추가 |
| `tests/` | 안정성 검증 | 신규 기능 및 오류 케이스 테스트 |

## 4. Unity 구현 후 추천 확장 순서

1. **Unity 통신 명세 확정**: 데이터 항목과 게임 이벤트 종류 협의
2. **DTO/스키마 정교화**: `dict[str, Any]` 대신 명확한 타입/범위/필수 필드 설정
3. **권한과 사용자 식별**: 기기별 계정, 방 입장 인증, 다른 사용자 정보 보호
4. **실시간 처리 결정**: 필요하면 폴링 대신 WebSocket 추가
5. **DB 진화**: 스키마 변경 관리(Alembic), DB 인덱스, 백업, 필요 시 PostgreSQL로 교체
6. **인터넷 배포**: 인증·HTTPS·관측성·CORS·리버스 프록시·서버 배포 환경 설정

## 5. 주의할 점

- 로컬호스트 바인딩(`APP_HOST=127.0.0.1`)은 외부 기기의 연결을 받지 않도록 하는 네트워크 설정입니다. **사용자별 접근권한을 제공하지는 않습니다.**
- SQLite는 작은 팀의 로컬 프로토타입에 적합하지만, 분산 배포용 메시지 브로커를 대체하지 않습니다.
- `StatePatch`의 `changes`는 깊은 병합이 아니라 **최상위 필드 단위 병합**입니다.
- 동시에 상태를 변경할 때 조용히 데이터를 덮어쓰지 않도록 `revision` 비교를 사용합니다. 클라이언트는 `409`를 처리해야 합니다.
- 이벤트 조회는 **클라이언트가 GET을 해야만** 새 메시지가 보이는 폴링 방식입니다. 종료/재시작 간 상태는 DB에 보존합니다.
- 데이터베이스 테이블이 변경되면 이미 생성된 SQLite 파일은 자동으로 변환되지 않습니다. 개발 단계에서는 기존 테스트 DB를 백업 후 초기화하거나, 운영 전에는 Alembic 마이그레이션을 도입해야 합니다.
