# 서버 ↔ 클라이언트 데이터 구조

> 대상 플로우: 회원가입 → 설문(페르소나) → 자취방 커스텀 → 재로그인 시 복원
> 서버: FastAPI + SQLite · 기본 경로 `/v1` · 필드 camelCase · 시간 ISO 8601 UTC
> 이 문서는 **`Server/app/schemas/` 의 Pydantic 모델과 짝**이다. 한쪽만 고치지 않는다.
> 전체 API 목록은 저장소 루트의 `API문서.md` 를 본다.

---

## 1. 플로우와 호출 순서

```
scene_login
  │  POST /v1/auth/signup          ← 신규 가입
  │     → accessToken, isNewUser=true
  │  GET  /v1/me
  │     → onboarding.nextScene = "scene_survey"
  ▼
scene_survey
  │  POST /v1/me/survey            ← 설문 완료 (닉네임·대사·페르소나)
  │     → character, onboarding.nextScene = "scene_room"
  ▼
scene_room
  │  PUT /v1/me/character          ← 캐릭터 꾸미기 확정
  │  PUT /v1/room/me               ← 가구 배치·벽지·바닥 확정
  ▼
(다음 접속)
scene_login
  │  POST /v1/auth/login
  │     → accessToken, isNewUser=false
  │  GET  /v1/me
  │     → onboarding.nextScene = "scene_room"
  │     → character + room 을 함께 받아 바로 복원
  ▼
scene_room
```

**`GET /v1/me` 한 번으로 복원이 끝난다.** 캐릭터·지갑·인벤토리·자취방을 한 응답에 담았다.
화면마다 쪼개 부르면 로딩이 여러 번 끊기고, 씬 분기 판단이 늦어진다.

---

## 2. 씬 분기는 서버가 정한다

클라이언트가 `character == null` 같은 조건을 조합해 판단하지 않는다.
조건이 늘어나면 양쪽에 같은 규칙을 두게 되고, 한쪽만 고쳐져 어긋난다.

```json
"onboarding": {
  "hasCharacter": true,
  "hasPersona": false,
  "nextScene": "scene_survey"
}
```

| 상태 | nextScene |
|---|---|
| 캐릭터 없음 또는 페르소나 없음 | `scene_survey` |
| 둘 다 있음 | `scene_room` |

클라이언트는 `nextScene` 값으로 `SceneManager.LoadScene` 을 호출하면 끝이다.

## 3. 인증 (구현 완료)

이미 동작하는 부분이라 계약을 바꾸지 않는다. `app/schemas/auth.py` 참고.

```
GET  /v1/auth/check-id?studentId=20241234   → { studentId, isAvailable }
POST /v1/auth/signup   { studentId, password }  → 201 AuthResponse
POST /v1/auth/login    { studentId, password }  → 200 AuthResponse
POST /v1/auth/refresh  { refreshToken }         → 200 AuthResponse
POST /v1/auth/logout                            → 204
```

```json
{
  "accessToken": "eyJhbGciOi...",
  "refreshToken": "f3c1a9...",
  "expiresIn": 3600,
  "isNewUser": true,
  "role": "user"
}
```

> `isNewUser` 만으로 씬을 정하지 않는다. 가입만 하고 설문 도중 앱을 끈 사용자는
> 다음 로그인에서 `isNewUser=false` 지만 여전히 `scene_survey` 로 가야 한다.
> 판단은 `GET /v1/me` 의 `onboarding` 이 맡는다.

## 4. 캐릭터 · 설문

### 4.1 설문 제출

```
POST /v1/me/survey
```

```json
{
  "nickname": "짭이",
  "catchphrase": "오늘도 과제 화이팅",
  "persona": "Diligent",
  "answers": [
    { "questionIndex": 0, "optionIndex": 2 },
    { "questionIndex": 1, "optionIndex": 0 }
  ]
}
```

**응답 200**

```json
{
  "character": {
    "nickname": "짭이",
    "persona": "Diligent",
    "catchphrase": "오늘도 과제 화이팅",
    "presetId": "chara_0",
    "parts": {
      "outer": "cloth_outer_0",
      "accessories": "cloth_acc_0",
      "clothTop": "cloth_top_0",
      "clothBottom": "cloth_bottom_0",
      "shoe": "cloth_shoe_0"
    }
  },
  "onboarding": { "hasCharacter": true, "hasPersona": true, "nextScene": "scene_room" }
}
```

- `persona` 는 `Diligent` / `Cheerleader` / `Tsundere` / `NightCoder` 넷 중 하나다.
  Unity 의 `MatePersonaType` enum 이름과 **문자열이 정확히 같아야 한다.**
- `answers` 는 판정 근거다. **서버는 이걸로 persona 를 덮어쓰지 않는다.** 판정 로직이
  클라이언트에 있어서, 서버가 다시 채점하면 규칙이 두 곳에 생긴다. 분석·검증용으로만 저장한다.
- 설문은 1회성이다. 이미 마친 계정이 다시 호출하면 `409 SURVEY_ALREADY_DONE`.
- 설문을 마치면 서버가 **기본 캐릭터와 기본 자취방을 같이 만든다.** 클라이언트가
  빈 방을 따로 생성 요청할 필요가 없다.

### 4.2 캐릭터 꾸미기 저장

```
PUT /v1/me/character
```

```json
{
  "nickname": "짭이",
  "presetId": "chara_1",
  "parts": { "outer": null, "accessories": "cloth_acc_0", "clothTop": "cloth_top_0",
             "clothBottom": "cloth_bottom_0", "shoe": null }
}
```

- **슬롯 5개만 보낸다.** 머리·눈·입·팔·다리·몸 같은 고정 파츠는 `presetId` 가 결정하므로
  주고받지 않는다. 보내면 서버가 무시해야 할 값이 늘어난다.
- 벗은 슬롯은 **`null`** 이다. 키를 빼지 않는다. 빠진 키를 "변경 없음"으로 볼지
  "벗음"으로 볼지 헷갈리기 때문이다. PUT 이므로 항상 전체를 보낸다.
- 서버 검증: 보유하지 않은 아이템 → `403 ITEM_NOT_OWNED`,
  슬롯이 맞지 않는 아이템(신발 칸에 모자) → `400 SLOT_MISMATCH`,
  없는 프리셋 → `400 INVALID_PRESET`.

## 5. 자취방

### 5.1 좌표계

Unity 의 `RoomGrid` 와 동일하다.

| 축 | 의미 | 기본값 |
|---|---|---|
| `gridX` | 가로 | 0 ~ 4 |
| `gridY` | 높이(층) | 0 ~ 3 |
| `gridZ` | 세로 | 0 ~ 4 |

- 1칸 = 1유닛 = 200px
- 칸 `(0,0,0)` 은 방의 최소 모서리
- 저장하는 값은 **점유 영역의 최소 모서리 칸과 회전**뿐이다. 크기는 `furnitureId` 로 조회한다

### 5.2 조회 · 저장

```
GET /v1/room/me          → RoomLayout
PUT /v1/room/me          → RoomLayout
GET /v1/room/{studentId} → RoomLayout  (권한 검사)
GET /v1/room/random      → RoomLayout
```

```json
{
  "studentId": "20241234",
  "ownerNickname": "짭이",
  "visibility": "public",
  "grid": { "width": 5, "height": 4, "depth": 5 },
  "wallpaperId": "wall_0",
  "floorId": "floor_0",
  "placements": [
    { "furnitureId": "furn_fridge", "gridX": 0, "gridY": 0, "gridZ": 4, "rotation": 0 },
    { "furnitureId": "furn_frame",  "gridX": 0, "gridY": 1, "gridZ": 1, "rotation": 0 }
  ],
  "updatedAt": "2026-11-14T05:00:00Z"
}
```

저장 요청은 `wallpaperId`, `floorId`, `placements` 만 보낸다. `studentId` 는 토큰에서 읽는다.

- **`grid` 를 응답에 포함한다.** 방 크기를 클라이언트에 하드코딩하지 않기 위해서다.
  5×5 가 좁아 6×6 으로 넓히는 변경을 서버만 고쳐서 적용할 수 있다.
- **`wallpaperId` 와 `floorId` 는 비울 수 없다.** 벽지와 바닥은 항상 하나가 선택된 상태다.
- `rotation` 은 `0 / 90 / 180 / 270` 만 허용한다.
- 내 방과 타인 방이 **같은 구조**다. 그래서 Unity 의 Room 씬이 파싱 코드 하나로
  본인 모드와 방문 모드를 처리한다.

### 5.3 배치 검증

클라이언트도 UI 단계에서 같은 검사를 하지만, **최종 판정은 서버**다.

| 사유 | HTTP | code |
|---|---|---|
| 방 밖으로 나감 | 400 | `OUT_OF_BOUNDS` |
| 가구끼리 겹침 | 409 | `CELL_OCCUPIED` |
| 공중에 떠 있음 (바닥 가구가 y>0, 벽 가구가 벽에 안 닿음) | 400 | `NO_SUPPORT` |
| 벽 전용 가구를 바닥에 놓음 | 400 | `INVALID_PLACEMENT` |
| 보유하지 않은 가구 | 403 | `ITEM_NOT_OWNED` |

```json
{
  "error": {
    "code": "CELL_OCCUPIED",
    "message": "가구가 겹칩니다.",
    "detail": { "gridX": 2, "gridY": 0, "gridZ": 0, "conflictWith": "furn_fridge" }
  }
}
```

## 6. GET /v1/me 전체 응답

```json
{
  "studentId": "20241234",
  "role": "user",
  "onboarding": { "hasCharacter": true, "hasPersona": true, "nextScene": "scene_room" },
  "character": { "nickname": "짭이", "persona": "Diligent", "catchphrase": "...",
                 "presetId": "chara_0", "parts": { "outer": "cloth_outer_0", "...": null } },
  "wallet": { "totalEarned": 1240, "balance": 380 },
  "inventory": ["furn_fridge", "cloth_outer_0", "wall_0", "floor_0"],
  "room": { "...": "5.2 와 동일" },
  "createdAt": "2026-11-01T09:12:00Z",
  "lastLoginAt": "2026-11-14T05:00:00Z"
}
```

`inventory` 는 가구·의상·벽지·바닥지를 **구분 없이 ID 배열로** 담는다.
분류와 표시 정보(이름·아이콘·크기)는 Unity 의 ScriptableObject 가 들고 있다.
서버가 같은 정보를 중복으로 들면 아트를 추가할 때마다 양쪽을 고쳐야 한다.

## 7. 저장 테이블 (SQLite)

| 테이블 | 키 | 주요 컬럼 |
|---|---|---|
| `users` | `student_id` PK | `password_hash`, `role`, `created_at`, `last_login_at` |
| `characters` | `student_id` PK/FK | `nickname`, `persona`, `catchphrase`, `preset_id` |
| `character_parts` | (`student_id`, `slot`) PK | `item_id` — 슬롯별 한 줄. 벗으면 행 삭제 |
| `survey_answers` | (`student_id`, `question_index`) PK | `option_index`, `answered_at` |
| `wallets` | `student_id` PK/FK | `total_earned`, `balance` |
| `inventory` | (`student_id`, `item_id`) PK | `acquired_at` |
| `rooms` | `student_id` PK/FK | `visibility`, `wallpaper_id`, `floor_id`, `grid_w/h/d`, `updated_at` |
| `room_placements` | (`student_id`, `grid_x`, `grid_y`, `grid_z`) PK | `furniture_id`, `rotation` |

- `character_parts` 를 `characters` 의 컬럼 5개로 만들지 않은 이유: 슬롯이 늘어날 때마다
  마이그레이션이 필요해진다. 행으로 두면 슬롯 추가가 데이터 변경으로 끝난다.
- `room_placements` 의 PK 를 좌표로 잡으면 **같은 칸 중복 저장이 DB 수준에서 막힌다.**
  다만 여러 칸을 차지하는 가구는 최소 모서리 한 줄만 저장하므로,
  겹침 검사는 서버 로직이 따로 해야 한다.
- 재화·인벤토리는 **전부 서버 권위**다. WebGL 빌드는 메모리 조작이 쉬워서
  클라이언트가 보낸 금액이나 보유 여부를 믿으면 안 된다.
